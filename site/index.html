What EMET is

EMET is an MCP (Model Context Protocol) memory server. It keeps persistent shared memory for AI agents and chats, so the work one host leaves behind is there for the next.

Layered memory
Six layers — identity, semantic, episodic, procedural, meta, and working — hold curated claims, split by what kind of thing an entry is. A correction writes a new entry, and the earlier one stays. Record.
Verified writes
Every write is read back and compared before it is reported as saved. Record.
Word-for-word transcript
A separate tier stores the conversation as it was written, so a summary cannot overwrite the record it came from. Record.
stdio and remote HTTP
Several hosts share one store: locally over stdio, and remotely over HTTP with OAuth. The transport changes and the store does not. Hosts.
MongoDB
Atlas, or MongoDB you run yourself. A one-machine trial can use MongoDB 6 or newer, and only the semantic_recall tool needs Atlas. Hosts.
Document control (ISO 9001 7.5.3 / ISO 13485 4.2.5)
No delete, on any store, by design. Corrections are made by adding: entries are superseded, documents are revised or retired, and retired means obsolete, not gone. Prior versions are retained, and templates are controlled documents. EMET supports that work; it holds no certification and claims no conformity.
Golem Expertise Module (GEM)
GEMs are gems of knowledge: a way for experts and others to package and share their knowledge and skills. A GEM extends EMET without changing the core. GEM.
RUNED GEM
A RUNED (Registered Utility Node Executable Directive) GEM carries tools the client runs. EMET records the result and does not run the tool. GEM.
Released check
EMET seats a GEM only when its author has explicitly marked it released, so an unfinished or test GEM cannot switch on by accident. Two older bundled GEMs are let through by a pin of their id, version, and every file instead. GEM.
Per-client attribution
The store has one owner. Every write is attributed to the client that made it, a new client is read-limited until it is approved, and guest, member, and sub-key access stay off unless you turn them on. Access.
Start
The first run needs Node.js 22 or newer and a MongoDB connection, then a short interview. Bot-team backup is off unless that interview records yes. Start.
The floor and the charter
The core floor ships with the server and cannot be switched off. The charter names the architecture those protections come from. Origin. The project.
MIT license
Version 0.2.6. EMET is still 0.x: stored document shapes may change before 1.0. Pin a version if you depend on them. The project.

One memory, several hosts

EMET is a bridge. Several AI hosts read and write one shared memory: desktop, command line, browser, phone, another vendor’s agent, bot teams, and single-session chats. Write a decision from one. Ask about it from another. It is there.

The store is MongoDB, Atlas or MongoDB you run yourself. A local host is launched by the client. A remote host adds your server’s address as an MCP connector and signs in with OAuth. Both use the same memory. The transport changes. The store does not.

How a host reaches the store

Two entry points ship over one source tree. They are not two projects. Both call the same dispatchTool in dispatch.js, which calls tools.js and database.js. src/index.js also imports validation.js. src/http-remote.js does not import validation.js or content_analyzer.js. tools.js imports the analyser.

src/index.js, stdio
Desktop and command line. The client launches it.
src/http-remote.js, streamable HTTP with OAuth
Phone, tablet, browser, and another vendor’s agent. Deploy this entry point.

The remote endpoint is OAuth-protected. A device is authorized once with the passphrase in EMET_OAUTH_PASSPHRASE, and the token persists across restarts and redeploys. PUBLIC_URL is the OAuth issuer. It must match the deployed URL exactly, or authorization fails in ways that look like a client problem.

  1. Deploy src/http-remote.js. The repository Dockerfile starts it. Without the Dockerfile, the start command is npm run start:http. Deploy walks through Railway and Fly.
  2. Register every host’s tag in EMET_SOURCE_TAGS before that host writes. Leave EMET_SOURCE_TAG unset when several hosts share one server. A default tag makes every host look the same.
  3. Add https://<your-host>/mcp as a remote MCP connector and finish the sign-in. A connector that only takes a fixed header or key will not work.
  4. Put the instruction block from Bootstrap in the project instructions. Where there is no such field, paste it as the first message.

Over HTTP, document, transcript, and memory writes use the source tag bound at approval. The caller does not pass source on those writes. A local stdio host still passes an exact tag from EMET_SOURCE_TAGS as source. Every entry records which machine produced it.

The guards that refuse an unregistered tag, on the main records and on another bot’s bots/ folder, are off unless EMET_SOURCE_TAGS is set. With it unset, any caller can write under any tag.

What each host is for

A single-session chat only works when you send it a message. It can’t watch EMET, and bots can’t message it. When a bot team needs that chat, the practice in the README is:

  1. The bots leave a task in EMET, in a document whose id they give you.
  2. You send the chat one line that names that document. The README’s example is: “Initialize EMET, read threads/open-tasks.md, do the task, and save the result to EMET.”
  3. The chat saves its draft to EMET.
  4. The bots check it.

The README names long drafting and review, done in one sitting, as a fit for the chat, and work in the repository, on the server, on a schedule, or in accounts as a fit for the bots. If the chat runs on a separate plan, its work draws on that plan’s allowance, not the bots’.

Grok Bot teams and single-session Grok chats can use the same server. What the bots save is there for a fresh Grok chat once it initializes, and the reverse. To connect a single-session chat, a Grok project or any chat host that takes a remote MCP connector and supports its OAuth sign-in, add https://<your-host>/mcp and complete the sign-in.

EMET also ships a plugin for Cursor and Grok Bot, in .cursor-plugin/plugin.json and mcp.json. The Cursor Marketplace listing is submitted and pending review. The plugin does not host memory. It connects to your own EMET server, so the records stay in your MongoDB.

  1. Deploy EMET remotely. Set PUBLIC_URL and a strong EMET_OAUTH_PASSPHRASE. Check that https://<your-host>/health returns {"ok":true,...}.
  2. Install the EMET plugin and set EMET_URL to https://<host>/mcp.
  3. Connect. The OAuth sign-in opens EMET’s passphrase page. Enter the passphrase once per device.
  4. Call emet_status with {"probe": true}. It writes, reads back, and removes a row from _emet_verify only. Then save_to_layer and recall that entry from another client.

The plugin also ships an emet-memory skill that tells the agent when to recall, save, and close a session.

One bot, one tag. In the same deployment, append the tag to EMET_SOURCE_TAGS, keep every existing tag in order, and append bots/<tag>/HANDOFF.md to EMET_RECORD_DOCS. A registered tag that is not listed as a bot can still write the main records. The hub’s tag is registered as a host and is never listed as a bot. After either variable changes, check /health and emet_status.

Opening a session on that host

Call emet_initialize with {} first and fetch every page it names. Ask for {"page": "all"} only on a host known to read long results whole. Pass the load_id from those pages to emet_session_open. An open with no load_id, with a page missing, or with a load_id the server has no record of, one from before a restart or 60 minutes past its last page, is refused, and the reply says what to call. A skipped page is refused before anything is written.

emet_initialize is served in pages so a host that cuts a long tool result still receives the startup. The page budget defaults to 18,000 bytes (EMET_INIT_PAGE_BYTES) and is clamped between 12,000 and 19,000. The example environment describes 20,000 bytes as the usual limit a host may cut at, and says to lower the page size only for a host that cuts shorter than that. page: "all" returns the whole startup in one result for a host with no size limit.

A session that has not initialized can read everything and can write only a new drop, drops/<date>-<slug>.md: its items, wrap-up, and handoff. A session with a registered source and the full startup has full access. Every initialized session sees unhandled drops first. New drops are capped at 20 per New York day, in one bucket: the whole local process on stdio, one shared visitor bucket for HTTP with no signed-in client, the source tag bound at approval when there is one, or that OAuth client otherwise. A source the caller types does not move the bucket. Drops are never deleted.

Hosts cache the tool list. After a deploy that adds or renames tools, each host keeps the old set until you reconnect the connector there. New tools stay invisible until then, and the host may ask again for approvals you had already given. Existing tools keep working.

Examples

A desktop or command-line client launches the stdio server and sets that host’s tag:

{ "mcpServers": { "emet": {
  "command": "node",
  "args": ["/absolute/path/to/emet/src/index.js"],
  "env": {
    "MONGODB_URI": "mongodb+srv://...",
    "MONGODB_DB": "emet",
    "EMET_SOURCE_TAG": "laptop"
  }
} } }

A phone, a browser, or another vendor’s agent uses the HTTPS endpoint. Claude, on every interface including a phone, adds a custom connector at that URL and enters the passphrase. Any other MCP client points at the same URL and completes OAuth. Then recall something saved from the other host.

https://<your-host>/mcp

curl https://<host>/health
curl https://<host>/.well-known/oauth-authorization-server

/health should report ok and a tool count. The well-known URL should return OAuth metadata, not a 404. A 404 means PUBLIC_URL is wrong.

Limits

  • A connector that only accepts a fixed header or key cannot sign in.
  • The passphrase is the whole perimeter. There is no second factor. Changing it and redeploying invalidates existing device authorizations.
  • Connecting the server gives an assistant the ability to remember. It does not make the assistant use that ability. Without the instruction block, it is less likely to search before answering, or to save a decision you did not ask it to save.
  • A phone, or a web project that cannot store a key file, does not take a delegated client sub-key. It uses the tag on its own connection. See Access.
  • The HTTP body limit is 256 KB. Tool calls are capped at 300 per minute for that person and client, and again per tool: 120 for recall and semantic_recall, 100 for query_layer, 30 for emet_status, 60 for save_to_layer, and 60 for every other tool.
  • An HTTP caller with no OAuth client id is stored as http:visitor, never in a stdio bucket.
  • Running cost for a single user is a small MongoDB cluster plus a hobby-tier container host. Both have free tiers adequate to start. The deploy notes say a small Atlas cluster plus a hobby-tier host runs in the low tens of dollars a month, and that both have free tiers adequate for a single user.

Who can join

The store has one owner, and other people can join only through the optional Guest (read-only) and Member (read and write) access, both off by default.

A new client, a bot or a single-instance assistant, is read-limited until it is approved. The approval is recorded. Every write is attributed to the client that made it. A declared source tag does not gain rights beyond the login it is bound to.

How joining works

Three places can say no, and none of them can widen another. The host decides what gets called and what data goes into the call. The server decides what it will do when asked. The database login, the role emetRecordKeeper, can insert and update, and it has no permission to remove anything from the record. A server cannot grant itself permission. Nothing in this repository can stop a host from asking before every call.

Two doors let a second person into this store. Both stay shut on a single-person assistant. Turn a door on only for a household or project store that is meant to be shared. The owner creates the code. The other person pastes it on the connect screen instead of the passphrase. A code expires in 14 days unless days says otherwise.

Guest, EMET_INVITES=1
emet_invite_create mints a one-time code. The only scope it accepts is emet.read. It is not Member access.
Member, EMET_MEMBER_ACCESS=1
emet_member_access_create mints a one-time code for a new person with emet.read and emet.write. It never makes them the owner. A display name is a label, not a credential: it never selects an existing person.

Redeeming a code allocates a new person id. If the slug of the display name is already taken, or it is the reserved id owner, the next free id is used (<slug>-2, then -3). An empty slug becomes guest. Linking a second device to an existing member is not inferred from a name.

A separate queue covers a new client on the owner’s store. A tag is known when it is in EMET_SOURCE_TAGS, already approved, or bound to a login at consent. The first write by any other tag is refused and queued in emet/CLIENT_APPROVALS.md, with who connected, the declared name, the client id, and what it tried to write. Hosts cannot write, patch, retire, or rename that document. Decide with emet_client_approve. Only the owner, or the chief-of-staff bot named by EMET_COS_TAG, may decide. Pending clients are listed to that reader by emet_initialize and emet_status. On a fresh store, the first solo client is approved as the owner’s primary.

A client may not decide its own approval. The connection that queued the request may not decide it either. decision is approve or deny. An optional reason is kept. When that client id already has approved tags, pass as add to keep them or rename to replace one.

EMET_STRICT_LOGIN_TAG=1 is off by default. With it on, a login’s bound tag is final: a write that declares a different source is refused, and so are emet_setup_complete and emet_initialize with a mismatched tag. Leave it off while bots share one login. Turn it on only once each bot has its own login, for example a Member code bound to its tag.

Delegated client sub-keys

One EMET, one owner login. If more than one bot or AI writes through that login, each bot that can keep a key file gets its own key. The server stamps the tag on the key. This is the same server, not a second product. It stays off unless setup is told that more than one bot or AI will use the memory, and the server has restarted with EMET_SUBKEYS=1. With the flag off, the tool list does not grow.

  1. Say “initialize.” Leaving the question out is the same as no. No leaves sub-keys off.
  2. Yes, on a server that reads .env, writes EMET_SUBKEYS=1, a generated pepper, and EMET_SUBKEY_PEPPER_VERSION=1 into that file after the identity documents are saved. They do not turn on in the process that is already running. Restart once. The tools and /owner/approvals appear together after that.
  3. Yes, on a server that takes settings from the platform, is refused before anything is saved. Set EMET_SUBKEYS=1, an owner-generated EMET_SUBKEY_PEPPER of at least 32 bytes, and EMET_SUBKEY_PEPPER_VERSION=1, then redeploy. Do not paste the pepper into the chat or into an EMET document.
  4. List each bot’s tag in EMET_SOURCE_TAGS before it asks. An empty list refuses every request.
  5. The bot calls emet_subkey_request. Approve it on /owner/approvals with the same passphrase used to connect a device. A correct passphrase opens a session of 15 minutes. The bot claims the key within 24 hours with emet_subkey_claim and keeps it where the other bots cannot read it. The key is never written into EMET.

A bot then opens a session with that key and passes the session handle on later writes. The server stamps the key’s tag, whatever source the caller sends. A key lasts 30 days (EMET_SUBKEY_TTL_DAYS, default 30, at most 90). To renew it, the bot asks again, you approve it, and the bot claims the new key within 24 hours. The previous key stays valid for EMET_SUBKEY_GRACE_MINUTES (default 10) while the bot switches. Earlier writes stay as they were written.

The four tools, registered only when the flag is on, are emet_subkey_request, emet_subkey_claim, emet_subkey_revoke, and emet_subkey_end_session. Write tools gain session_handle. emet_session_open and emet_session_close gain subkey.

What the tools are allowed to do

Thirty tools are registered with sub-keys off. Every tool declares MCP annotations in src/annotations.js: readOnlyHint, destructiveHint, idempotentHint, and openWorldHint. The hints let a host stop asking about reads. They are hints, not enforcement. What is actually auto-approved is a host-side setting. openWorldHint is false on every tool. The tools reach this server’s database and nothing else: no filesystem and no shell. The sign-in server fetches a client’s metadata document, and only from a public address it has already checked.

11 read-only
emet_gaps, emet_floor, recall, semantic_recall, corpus_recall, query_layer, query_transcripts, read_doc, read_doc_history, list_docs, validate_doc. These cannot change the store under any arguments.
10 additive writes
emet_initialize (it can provision a missing board; it stays a read), save_to_layer, revise_memory, save_transcript, revise_transcript, emet_session_open, emet_transcript_append, emet_session_close, rename_doc, accept_nonconformance. They add. They do not remove or replace. Opening a session still needs emet.write, because it stamps the drop list a board edit trusts.
7 that replace or hand out access
write_doc, patch_doc, restore_doc, emet_setup_complete, emet_invite_create, emet_member_access_create, emet_client_approve. Prior versions of a document are archived first. A code that grants access is marked the same way.
retire_doc and emet_status
retire_doc marks a document obsolete and keeps its id and content. emet_status is not read-only: with probe: true it writes, reads the same value back, and removes that document. It does not drop the collection. A read-scoped token may call it without probe.

A reasonable default, from the permissions doc, is standing approval for reads, per-call or standing approval for additive writes, and eyes on the replacing writes, including setup and the two access doors. Do not carry that posture to a filesystem or shell server. A wrong call there can do something no archive brings back.

Examples

On a single-person install, leave both doors commented, as .env.example ships them:

# EMET_INVITES=1
# EMET_MEMBER_ACCESS=1

The owner decides a pending client by tag. Nothing is changed if tag or decision is missing or wrong:

emet_client_approve
{"tag": "<tag>", "decision": "approve"}

A guest code takes a display name and only emet.read. A member code takes a display name. When a registry is set, pass source as an exact member of EMET_SOURCE_TAGS. A member needs that tag to write documents over HTTP while a registry is set.

Limits

  • Both doors are off unless the matching variable is 1. A single-person assistant store stays private. A later shared space does not copy a personal EMET into the room.
  • A guest invite accepts only emet.read. A member is never the owner. Only the owner can create either code. Over HTTP those codes require an owner person. The local stdio client is the owner.
  • A read-only token can call emet_initialize and cannot open a session. emet_session_open, and emet_status with probe: true, need emet.write. An HTTP token with no scopes is not the owner. The consent page shows the scopes it is granting.
  • Sub-keys apply only to authenticated HTTP. Stdio keeps the registry rules. Invite and Member Access logins cannot request, claim, or present a sub-key. A sub-key never grants more than the owner login, and it cannot call the owner-only tools, including approve, invite, member access, and setup.
  • What a sub-key shows is that a write was made with a key you approved. If several bots can read each other’s files, EMET cannot prove which program was holding the key. Revoke a leaked active key with emet_subkey_revoke from the owner’s login. Deny applies only to a pending request.
  • Revoking the owner login stops every sub-key. They hang off that login.
  • The pepper is a server secret. It is not stored in the database, in a document, or in the answer setup gives the assistant. A hosted server does not get a pepper written into its container.
  • With EMET_SOURCE_TAGS unset, an unregistered tag is not refused. Set the list before more than one host or bot writes.

What stays on the record

A correction writes a new entry. The earlier entry gets an end date and stays visible, marked with what replaced it. Current entries are listed first. The earlier one is still there to read. An episodic event is immutable. Events do not get revised, and a later entry corrects the reading of it instead of putting an end date on the event.

Two tiers stay separate. Tier 1 holds curated claims in six layers. Tier 2 holds the conversation as it was written, so a summary cannot overwrite the record it came from. EMET verifies the record, not the computation.

The six layers

An entry is filed by what kind of thing it is, not by topic. Each one carries an importance score and optional temporal validity. src/layers.js ships the charter for all six, and emet_initialize returns it, on a new store and on an established one.

identity
Who the assistant is and who it serves. Importance 0.9 to 1.0. Written rarely, by design.
semantic
Facts that stay true regardless of when they were learned. Importance 0.6 to 0.9. Written when a durable fact is established or corrected.
episodic
What happened, and when. Importance 0.4 to 0.7. Written at session close and at milestones. Not revised.
procedural
How something is done, and decisions that govern later action, with the reasoning. Importance 0.5 to 0.8.
meta
What is visible only from outside the exchange: how the memory behaves, and how the assistant behaves toward the user. Importance 0.6 to 0.9.
working
Short-lived context and notes for whoever picks the work up. Importance 0.3 to 0.6. An unlabelled write lands here.

Episodic, semantic, and procedural are about the world. Meta is about the system. In the deployment this design came from, the meta layer sat nearly unused for about a year: the collection existed, and the tools accepted writes, and it was not the obvious place to put anything. assessLayerHealth() reports a layer that has gone dark. It reports. It never blocks, and it stays silent on a store too new to have a pattern.

How a write is checked

There is one door for each store: saveMemory for the six layers, writeDoc for documents (patch_doc delegates to it), and saveTranscript and reviseTranscript for the verbatim tier. tests/write-path.test.js fails the build if a MongoDB write in src/ sits outside those functions, and if anything removes from a layer, document, or transcript collection.

  1. Secrets are masked before anything is stored or hashed (src/redact.js). Credentials inside URIs, bearer tokens, JWTs, EMET_SUBKEY_PEPPER, and key: value pairs whose key names a secret become *****. The receipt’s redacted count is the spans this write changed.
  2. The source tag is decided here. Over HTTP it is the tag bound at approval. On stdio it is the caller’s exact registered tag, else the environment default marked source_defaulted, else null marked source_missing.
  3. A missing accountability field becomes a visible marker, such as provenance_missing or importance_defaulted, because a missing value can be queried and an absent field cannot. One refusal: a semantic or procedural entry with no source is not written.
  4. Content and metadata are digested into their own columns, read back, and compared before the write is reported as saved. The id is checked by content, not by mere existence, because ids come from a counters collection.

That read-back is src/aleph.js. A database error means the store could not be reached and the write probably did not happen. An AlephError means the call succeeded and the store does not contain what it should. It is not flattened into “the save failed,” and it is not retried blindly.

Later reads ask a second question: is the row still what was recorded? Each row carries content and metadata digests, an HMAC over both when EMET_SIGNING_KEY is set (the key stays on the service; unset means the entry is saved unsigned), and a link in its layer’s hash chain. recall, query_layer, and semantic_recall recompute the digests and attach integrity: true, false (the row is returned and flagged, never dropped), or unattested for a row written before the column existed. emet_gaps walks the chain and counts a row altered after writing (broken_chain) or removed from mid-chain (chain_discontinuities). The expected count for both is zero. emet_gaps identifies holes and never fills them.

revise_memory writes a new entry carrying supersedes and marks the parent with superseded_by and superseded_at. Nothing is edited or deleted, and the parent is not hidden. The new content has to stand alone. Episodic is not in the layers revise_memory accepts. When a later entry corrects only part of an earlier one, it carries metadata.corrects set to the parent id, same layer. A missing parent is refused before anything is written. The parent’s content, digest, and liveness stay untouched. Its corrected_by list gains the new id. corrected_by is a door marker. A caller cannot set it.

recall ranks by how many of the query’s words match, then by importance. Current entries come first in every order, including time order. Pass order: "latest" for time order. A superseded or expired entry stays in the result, marked with its end date and the id of what replaced it. Pass history: true when current matches fill the limit and you still need the ended ones. The store ranks before it keeps a window of at least 200 rows, or 20 times the page. A word matches as written, so $gt is that text. Capital and lower case match, including École and école. İ matches only itself.

An entry can point at the transcript span it came from: session_id plus a range of exchange indices, stored as derived_from. An entry consolidated from other entries carries {entries: [...]} instead of a guessed timestamp. The pointer wins when it is present. The timestamp is the fallback when the pointer is null. They are not averaged. Entries written before pointers existed keep a null pointer and are not backfilled. crossCheckProvenance() reports a pointer and a timestamp that disagree.

Documents and the transcript

No tool removes a memory entry, a document, or a transcript. The database role is not granted remove on the record either. A document is revised or retired. retire_doc marks it obsolete and keeps its id, content, version, and digest. read_doc still returns it, flagged retired, with the reason. Every document write archives the copy it replaces. read_doc_history lists what is retained and returns any retained revision in full, checked against its stored digest.

Records, including the handoff and any id in EMET_RECORD_DOCS, are superseded whole. patch_doc is refused on them. A new revision is written in full and names the version it supersedes. Templates are controlled documents. The shipped copy governs. validate_doc checks form and continuity, and the same check runs inside the write path, where no caller can skip it. A record that fails is marked and kept, never silently accepted or discarded. It stays counted at session start until a later revision corrects it or accept_nonconformance dispositions it. Whether an answer is true is not something this check decides.

The server provisions a blank board at setup. No session can write the board as a new document. It is edited with patch_doc and a reason. Once any working document exists, it is edited, not rewritten. A change that leaves a document under half the size it had when this session first touched it, or under half of its largest size in the last 24 hours, is refused. retire_doc refuses a working document. rename_doc issues a new id and marks the old id retired. The text stays readable and stays in the list. restore_doc is the one whole-document recovery, for an owner-listed tag, and only a stored conforming revision whose digest matches. A record is not restored. A shipped copy is never restored.

The transcript path stores exactly what it is given. If a payload will not transmit, split it across parts. Do not compress it. save_transcript does not read a file path. The caller passes the exchanges. A transcript field is capped at 32,000 characters, and the whole transcript request at 256,000 characters. query_transcripts reads the live transcript store and the legacy exchange archive together, each result naming the collection it came from. Nothing is migrated between them. revise_transcript writes a corrected part and must keep exactly the same exchange numbers.

At the end of a session the assistant writes four things: the handoff, the state document, an episodic entry, and the verbatim transcript. emet_session_close checks that each one landed and returns state: "complete" only when they did. It does not write those artifacts. A tool that generated a summary would be manufacturing the record. Receipts are required, and each one is compared with the store. A mismatch returns blocked. Three blocked closes on one session return escalate. After a complete close, the session takes exactly one more append, its closing exchange, within EMET_CLOSE_GRACE_MINUTES (default 5, at most 60), and is then locked.

A bot in a long-running chat saves its transcripts word for word at least nightly, under the open session or a daily YYYY-MM-DD_chat-daily session. Prefer event triggers over time-based polling. When polling is unavoidable, use the longest interval the job allows. Never reconstruct turns. Mark gaps as gaps. Session close cites those saved parts.

The door guards each write. The monorail, src/session-graph.js, guards the order: open, work, record, board, handoff, close. Every skipped step is refused, and the refusal says how to pass. There is no report mode and no off switch. EMET_SESSION_GRAPH is no longer read. Switches at the junctions are designed, not yet built. The monorail’s turn coverage is only as strong as the exchange numbers hosts report, and it never sees the reply text.

Limits

  • Nothing in the record is deleted. Corrections are new writes. Retired means obsolete, not gone.
  • The store does not promise that every write is complete. It does promise that every write is attested, attributed, and scrubbed, and that every absence it can see is visible.
  • validate_doc checks form and continuity. It does not check whether an answer is true.
  • EMET does not run a GEM’s computation. A client-executed result is recorded as the client attested it. It can be replayed from the recorded inputs. EMET does not re-execute it.
  • Two content routers are carried from upstream. Measured against a 1,175-row corpus, they agree with the stored layer well under half the time (41% and 36%), so neither places entries. An unlabelled write lands in working, flagged, with both opinions kept in routing.
  • consolidation_candidates in emet_gaps is tag overlap, not semantic similarity.
  • Rows written before 2026-09-05 carry no content digest, and rows written before 2026-09-07 carry no metadata digest. Reads report them as unattested. They are not backfilled.
  • save_transcript’s description does not state that it stores content verbatim. The implementation does.
  • There is no export, import, or restore-and-compare.
  • The document store is not prefixed, so one database holds one instance’s identity. Run separate databases if you want separate memories.
  • EMET supports document-control work. It holds no certification and claims no conformity. An organization that uses it stays responsible for its own quality system, including validating EMET for its intended use.

First run

On the first run, say “initialize.” The assistant asks a short interview and records it with emet_setup_complete, which also creates the owner person. After that, the same word opens a session that already knows where things stood. There is no separate setup command to memorize. The branch happens inside the tool.

The interview asks eight things, four required and four optional. The assistant asks them one at a time, not as a form.

Required
What the assistant should be called. How it should carry itself. Your name, in the form you want used. What you are using this memory for.
Optional
How you want to be worked with. This host’s source tag. Whether more than one bot or AI will use this memory. Whether to turn on bot-team backup.

Leaving the multi-bot question out leaves delegated client sub-keys off. A yes writes them only when this server reads .env, and they take effect on restart. A hosted server refuses and names the three variables to set, then redeploy. See Access.

Bot-team backup is off unless the interview records yes. Yes is the recommended choice. The words Yes and Yes. count as yes. No, or leaving it out, leaves it off. A non-string and any other text are refused before a write. The answer is stored on bootstrap/USER.md. EMET does not copy prompts or settings itself, and secret values are never stored. The recipe and the recovery template ship as the bundled bot-team-backup GEM, at gems/bot-team-backup/guides/BOT_TEAM_BACKUP.md.

What gets written: bootstrap/IDENTITY.md, bootstrap/USER.md, and an entry in the identity layer. All three are read back before setup reports success. Edit any of them later with write_doc. The same versioning applies. A read-scoped emet_initialize writes nothing. A write-scoped one may provision a missing board.

Setup refuses to finish on partial answers rather than inventing an identity. If the store cannot be reached, initialize says so instead of proceeding as though memory were available. emet_setup_complete is refused under a bot tag. On a store where bootstrap/IDENTITY.md and bootstrap/USER.md already exist, it is refused unless reissue: true is passed on the owner’s explicit word. Nothing is written on that refusal. When a reissue does run, the previous copy is archived. Nothing is overwritten in place.

Every session after that

Say “initialize” as the first message, on every device, before the question you came to ask. emet_initialize returns who the assistant is, who you are, where things were left, and the operating disciplines. Fetch every page it names, or pass {"page": "all"} on a host with no size limit, then emet_session_open with that startup’s load_id.

Before it asks you anything, it names items from the handoff and state documents: anything left half-finished, what is dated in the next seven days, each open item you own with its next action, and whatever was left undecided. A count, or a bare “where do you want to start?”, is not treated as a startup.

Say “wrap up” at the end, or goodbye, or that you are opening a new session. The assistant writes the handoff, the state document, an episodic entry, and the verbatim transcript, then calls emet_session_close. Wait until it returns state: "complete" before you close the window. If it comes back anything else, something did not save, and the reply says which. Close without that and the next session inherits a hole. emet_gaps will count it.

Connecting the server does not make the assistant use it unprompted. Paste the block from Bootstrap into the project instructions. On a host with no such field, paste it as the first message.

Where EMET came from

EMET was built by Dreamforge Studio LLC from a neurodivergent user’s own need for an AI assistant that remembers. The word coined for that is neurendipity: neurodivergent and serendipity.

It is designed first for neurodivergent users, and it works for anyone.

The name

אמת is Hebrew for truth. EMET is also an acronym: Enduring Memory & Epistemic Tiers. Both halves are load-bearing.

In the golem legend the word אמת is inscribed to animate the body, and erasing its first letter leaves מת, met, dead. That is why the verification layer is called aleph. emet_initialize is the call that hands the model an identity, the person it serves, where things stood, and the disciplines it is bound by. Nothing mystical is claimed. It is a description of what that first tool call does.

Enduring is measured against what a language model is by default: a session that starts from nothing and ends by forgetting. Epistemic tiers are how that record stays checkable. Tier 1 holds curated claims. Tier 2 holds the verbatim record that justifies them. They are kept separate so neither can overwrite the other. The mechanism is on Record.

Neurendipity, the bundled GEM

The GEM specification describes EMET as a memory server. Its function is the record: what was written, what was decided, and what still stands. It is not a behavior framework. Behavioral guidance lives in GEMs. The core floor is the lines every install serves and nobody can switch off. The spec names integrity, honesty, no sycophancy, truth over speculation, fact-checking, and persistence. They ship in server code. Setup cannot write them. A GEM ranks below that floor and below the user’s current word, and it cannot remove a protected floor line.

Version 0.2.5 added two core floor lines. goal_check: before multi-step work, on an ambiguous request, or when the conversation turns, state the person’s goal and underlying problem in one sentence in your own words, marked as your read, and confirm. no_rapport_mirroring: no echoing, flattery, or agreement to build rapport or seem attuned. Agreement is earned by substance. The 0.2.6 changelog records that the floor is unchanged.

Neurendipity is the bundled GEM for neurodivergent engagement and autistic burnout support. It is support only, not counseling or treatment. It ships installed and stays off unless EMET_ACTIVE_GEMS=neurendipity. emet_floor takes a gem argument to read an installed GEM’s floor without turning it on. The guide id guides/NEURODIVERGENT_SUPPORT.md still resolves, for one release, to that GEM’s copy. The example at gem-library/examples/neurendipity/ is a shape, not the installed GEM.

A GEM may declare a tool. EMET does not run that computation. The client runs the tool, and what is written back is checked the same way as any other write. A GEM is seated only when its released flag is the boolean true. A missing flag is refused except for a legacy manifest pinned by id, version, and file digests. The GEM specification in this repo is Draft, revision 2026-10-12. Its canonical home is the private repository EMET-GEMs. The copy under review is gem-library/.

Golem Expertise Module (GEM)

GEMs are gems of knowledge: a way for experts and others to package and share their knowledge and skills. They extend EMET without compromising the core architecture.

A Golem Expertise Module (GEM) is optional guidance that seats in the socket. The name marks the golem legend: the word אמת, truth, animates the figure. The core floor stays the memory minimum and cannot be switched off. Behavioral guidance lives in the GEM. The floor ships in server code. Setup cannot write it, and it cannot be lost, edited away, or forked per install. An active GEM ranks below that floor and below the user's current word. It may add lines. It cannot remove a protected floor line.

How a GEM sits on the core

The socket is that seat, not a host connector and not a network socket. It seats bundled GEMs from the gems/ directory inside a release, and nothing else. A folder someone drops in, a document in the store, or a fetch from the network is not loaded. The socket does not discover a user-supplied path.

When the core floor, the user's current word, a GEM, and a character modifier speak to the same point, they rank in that order, highest first. The user can ask for more care, more explanation, or a different pace. The user cannot turn off honesty, persistence, or fact-checking.

A GEM adds its own sections. It must not use the core keys voice, engagement, persistence, corpus_discipline, or operating_discipline. An override of a core protection path fails gem-check. Text that tells the model to ignore the floor fails the floor-negation lint, and a line that passes the lint still loses to the core floor. The lines that moved into Neurendipity were not copied into a second always-on document.

A person may write a GEM. That person may not change the standard, the schema, or the socket rules. Those change only by a GEM Enhancement Proposal.

A plain GEM and a RUNED GEM

RUNED (Registered Utility Node Executable Directive) is one declared, registered tool built into a GEM. A RUNED GEM is a GEM whose manifest contains one or more of those directives.

kind gem
Engagement lines and guides. runes is empty. No code file is listed.
kind runed-gem
The same, plus one to sixteen RUNED directives. Lean Six Sigma is the bundled example. Its directives are calculators.

A RUNED directive is client-executed code. The socket serves it while the GEM is on and does not run it. There is no fallback that runs it for a client that has no sandbox. That client gets no result and must say so. One read-only tool per directive is named gem_<gem>__<rune>. A call returns the code, the description, the inputs, the outputs, the runtime, and the served sha256. The client runs the code. A kept result goes back through the same write path as any other write. EMET verifies the record, not the computation. It does not re-execute the tool.

The five Lean Six Sigma calculators, each a RUNED directive that does not write, are:

  • lss_capability computes Cp, Cpk, Pp, or Ppk from the mean, sigma, and specs on the call, and returns assumption flags.
  • lss_dpmo_sigma computes DPO, DPMO, and opportunity yield from defect counts. It does not invent a sigma level.
  • lss_control_limits computes three-sigma control limits for xbar-r, i-mr, p, np, c, or u.
  • lss_sample_size computes a normal-approximation sample size for a mean or a proportion. The result says it is a margin-of-error figure.
  • lss_hypothesis computes a one-sample t, a chi-square goodness of fit, a one-way ANOVA, a simple regression, or a confidence interval. It does not return a p-value.

How a GEM is checked and seated

gem-check takes the GEM directory. It reads gem.schema.json from the checker, not from the GEM. This revision accepts spec 2026-10-12 only. Exit 0 means every required check passed or was skipped as specified. A failure refuses that GEM. emet_initialize still returns, and gems_available lists the GEM with loadable: false and the check id.

  1. Discover child directories of the release's gems/. Do not discover the document store, the network, or a user-supplied path.
  2. Validate with the checks in the conformance list.
  3. Load the floor of each GEM that validated. Do not register tools yet.
  4. Activate a GEM whose defaultOn is true, or that the install asked for, subject to the caps. Register RUNED tools only while that GEM is on.

EMET only seats a GEM its author has explicitly marked released, so an unfinished or test GEM cannot switch on by accident. Only the boolean true counts. false, the string "true", 1, and null fail. A missing field is allowed only for Neurendipity 1.2.3 and Fieldnote 1.0.1 when the id, the version, and every file digest match the pin. A shorter file list does not match. The pin covers the id, the version, and the file digests. It does not cover the other manifest fields. Any other GEM missing the field is refused, including a bumped version of those two. The check runs on every boot.

Turning one on

EMET_ACTIVE_GEMS is a comma-separated list of ids. Unset means only a GEM with defaultOn true is active. Every bundled GEM in this release has defaultOn false, so an unset list leaves them off. emet_floor takes a gem argument and reads an installed GEM's floor without turning it on.

EMET_ACTIVE_GEMS=neurendipity
EMET_ACTIVE_GEMS=lean-six-sigma
EMET_ACTIVE_GEMS=neurendipity,lean-six-sigma

emet_status reports each GEM's byte cost in gems: installed and active counts, active floor bytes against the cap, headroom, and per-GEM id, version, kind, bytes, and refusal reason. The field is read-only and carries no floor text. A socket failure is reported there and does not fail the status call. The bytes in that report are the trusted floor bytes the socket counts toward the cap. The specification also says the served code counts toward the GEM's byte cost.

The caps the socket enforces are 16 installed GEMs, 4 active GEMs, and 16,384 bytes of active floor files. A floor file is at most 8,192 bytes. One guide is at most 65,536 bytes, at most 16 guides, and the sum of listed file sizes is at most 262,144. Going past the active count or the floor-byte cap refuses that GEM. The others still seat.

Bundled GEMs, controlled templates, and the RUNE load gate. Fieldnote is off by default and is not a user-facing GEM.
site/
This page. .github/workflows/pages.yml publishes the folder to GitHub Pages for dreamforgestudiollc/EMET on main.
tests/
npm test runs every *.test.js on one shared harness. No framework, no database, no credentials. The README recorded 1,852 checks across 64 suites on 2026-10-07, and it does not keep per-suite counts because they go stale. npm test prints the current lines.

package.json files ships src/, verification/, templates/, guides/, gems/, top-level docs, CHARTER.md, CHANGELOG.md, server.json, .env.example, README.md, and LICENSE. It does not ship tests or .env.

Two checks hold the no-delete line. write-path.test.js fails if anything in src/ removes from a layer, document, or transcript collection. atlas-role.test.js fails if the database role grants remove. Open an issue before a pull request for anything beyond a typo. The feature template asks the four questions the charter asks of every change. Run npm ci && npm test. The charter, the core floor, the README’s document-control section, attribution, and the GEM standard change only by the maintainer’s decision.

Examples

npm install
npm test
npm start
npm run start:http

npm start is the local stdio server. npm run start:http is the remote server. A release is published from the repository. Only the latest release receives fixes.

Limits

  • Still 0.x. Breaking changes to stored document shapes may land before 1.0.
  • No export, import, or restore-and-compare yet.
  • The document store is not prefixed. One database holds one instance. Use separate databases for separate memories.
  • Dynamic Client Registration is still served beside Client ID Metadata Documents. It is scheduled to come off on 2027-06-01. The MCP specification’s deprecation window closes around 2027-07.
  • Delegated client sub-keys stay off unless setup is told that more than one bot or AI will use the memory. A hosted server does not write a pepper into its container. A stamp shows that an approved key was presented, not which program held it.
  • save_transcript’s description does not say that it stores content verbatim. The implementation does.
  • Monorail switches are designed, not yet built. The session-order check never sees the reply text.
  • Securing the deployment is yours: the host, MongoDB, and EMET_OAUTH_PASSPHRASE. Report a vulnerability in EMET’s own code privately, through GitHub security advisories, not in a public issue. Include the version, the transport (stdio or remote HTTP), and steps to reproduce. Do not include real passphrases, tokens, connection strings, or memory content.
